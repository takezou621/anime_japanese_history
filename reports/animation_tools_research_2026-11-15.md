# アニメーション系ライブラリ18件 調査報告（anime_japanese_history への適用可否）

作成: 2026-11-15（監督: Muse／調査: 公式リポジトリ・公式ドキュメント・npm/PyPI を実地確認）

## 適用先の現状と弱点

現行パイプライン: 台本JSON → VOICEVOX音声 → 静止画アセット（背景・キャラ立ち絵・カード）→ Python + ffmpeg の assemble.py で合成（カット切替のみ、字幕ASS）。

- (a) キャラが静止画（口パク・瞬き・頷きなし）
- (b) 年表・図解・カードが静止画でアニメーションしない
- (c) 画面遷移がカットのみ
- (d) 数字・年号のカウントアップ、桜吹雪・雨等のパーティクル演出がない
- (e) 地図・古墳・城などの3D表現がない
- (f) Shorts（縦型・一問一答）の量産手段がない／告知用GIF需要

## 結論（推奨順）

### 第1推奨: Manim（図解インサート生成）
- Python製で現行パイプラインと同居。図解シーンを透過MOV/WebMで書き出し、既存 assemble.py に overlay する「前段追加」で、現行フローを壊さず段階導入できる
- 効く弱点: (b)◎ 年表の線が伸びる・系図/因果フローの出現と強調、(d)◎ 年号・石高などのカウントアップ（ValueTracker の定番パターン）、(e)○ 台本JSONから量産＋解像度変更で縦動画化、(f)○ GIF直接書き出し
- ライセンス MIT。保守活発（v0.22.1、2026-10-27）。ただし大規模リファクタ中のためバージョン固定推奨
- 日本語: `Text()`（Pango経由）で対応可。`Tex()` 系は日本語と相性が悪いので使わない
- 注意: レンダリングはCPU（Cairo）で長尺は遅い。数秒〜数十秒のインサート専用に限定する

### 第2推奨: Remotion + 公式 Skills（戦略的本命／Shorts量産と将来のeditor置換候補）
- 「AIに動画を作らせる」提示文脈に直接応える唯一の候補。Skills（remotion-dev/skills）はAIエージェントに Remotion コードを書かせるための公式知識パッケージで、実行系は Remotion 本体（Reactで動画を記述しフレーム単位で決定論的にレンダリング）
- 効く弱点: (b)◎ SVG/JSXで図解を直接描画しアニメーション、(c)◎ 遷移・スプリング標準装備、(d)◎、(e)◎ Compositionをprops駆動にすればクイズJSONから縦型Shortsをバッチ量産（最も得意な使い方）、(a)△ 口パクは口開/口閉PNGのフレーム切替で実装可
- ヘッドレスバッチレンダリング可。透過動画（WebM VP9 alpha / ProRes 4444）公式対応で、現行ffmpeg合成への段階移行も可能
- ライセンスは独自（MITではない）: **個人・従業員3名までの営利組織は無料で商用可**（収益化YouTubeも Unlimited commercial use と明記）。4名以上の営利組織は Company License（$25/月・席〜）。5.0でライセンス変更の予告あり、採用時はバージョン固定
- コスト: React/TypeScript の学習コストは最大級だが、Skills 前提でAIに書かせるなら緩和。日本語は @remotion/google-fonts/NotoSansJP が公式提供。フォント読み込み待ち（delayRender）をしないとフォールバック字体が焼き込まれる事故に注意

### 第3推奨: Godot（モーション層の代替候補）
- 公式 Movie Maker モードで透過PNG連番＋WAVを決定論的に書き出せる（フレーム落ちが原理的にない）。既存の背景PNG・立ち絵をそのまま素材にでき、上下動・瞬き差分切替・カメラパン・図解アニメ・2Dパーティクル・遷移クリップを1つのツールでカバー
- 効く弱点: (a)○ (b)○ (c)○ (d)○ (f)○ と最広。(e) 本格3Dは Blender に劣る
- ライセンス MIT。保守は極めて活発（スター約120k）
- 注意: ヘッドレス運用に癖（Linuxは Xvfb + ソフトウェア描画が実務解、macOSではウィンドウ遮蔽でフレーム複製の報告あり）。GDScript と第2ツールチェーンの維持コスト
- Remotion と役割が重なるため、モーション層はどちらか一方に寄せる。AIエージェントにコードを書かせる制作モデルとは Remotion の方が相性が良い、というのが監督判断

### 限定用途で有効
- **Blender**: (e) 3Dインサート専用機。前方後円墳・城・地形を bpy で自動生成し、回転・フライバイの透過連番を量産。EEVEE のトゥーン寄せで絵柄と両立しうる。本体GPLだが成果物は制作者の完全な所有物。学習コスト最大だが用途を絞れば現実的。GPU前提（Mac mini 上で実行）
- **Proton**: (d) パーティクル特化の最小追加。CanvasRenderer 透過＋ヘッドレスChromeでフレームPNG化し ffmpeg に載せる。桜吹雪・雨・雪・炎が数十行で作れる。Godot/Remotion を入れない場合の選択肢
- **Konva**: JS路線で既存PNGアセットを動かすなら最有力（Node公式対応、Tween内蔵）。ただしタイムライン管理は自前。Remotion を採るなら不要
- **Lottie Web**: 既成素材（トランジション・装飾）の借用限定。オーサリングがAE前提で自動生成フローと思想が逆

### 見送り
- **Motion Canvas**: (b) 図解の目的適合性は高いが、保守が実質停止（安定版 3.17.2 は2024-12、コミットは2025-02で停止）し、レンダリングがエディタ手動操作でバッチ自動化できない。10話+Shorts の量産運用に不向き
- **TweenJS**: 開発が2018年で終了。新規採用の根拠なし
- **Motion / Anime.js**: 動画書き出し基盤を持たず、使うなら結局 Remotion 等のホストが必要
- **Shifty / Ola**: 数値補間の小部品。Ola は実時間依存でフレーム決定性と相性が悪い。いずれも Manim/Konva/Remotion の内蔵機能で代替可能
- **Two.js**: 描画専用でトゥイーン/タイムラインがなく自前実装が多い。同用途では Konva に劣る
- **gifenc**: GIF専用の小部品。Python+ffmpeg の palettegen でも代替可能
- **LUME**: alpha継続・単独メンテナ。できることは Three.js で直接できる
- **Babylon.js**: Three.js と重複し、オフライン決定論書き出しが弱い（VideoRecorder は WebM・実時間のみ）
- **Three.js**: コードだけで3Dインサートを量産したい場合の Blender 代替。併用はせず片方に寄せる

## 導入の順序（監督提案）

Season 1 は現行パイプラインで完成させる（制作中の基盤差し替えはしない）。以下は Season 2 以降／パイプライン改善フェーズの順序:

1. **Manim の PoC**: 年表シーン1本を透過インサートで試作し、現行 editor に重ねて画質・工数を確認（最小リスク・即効性）
2. **Remotion の PoC**: クイズJSONから Shorts を1本バッチ生成し、量産適性と日本語フォント周りを確認
3. 結果を見てモーション層の主軸を決定（Remotion 全面移行か、Manim併用+現行editor継続か）
4. 3Dインサートが欲しくなった時点で Blender を限定導入
